# 4.5 인덱스

> 핵심: **읽기 성능을 높이기 위해 추가 자료구조와 저장 공간을 사용하는 것**

---

# 4.5.1 인덱스의 필요성

## 1. 인덱스란?

인덱스(Index)는 데이터베이스에서 원하는 데이터를 빠르게 찾기 위한 **별도의 탐색 자료구조**다.

책의 색인과 비슷하다.

```text
책 전체를 처음부터 읽기
vs
색인에서 단어를 찾아 해당 페이지로 이동
```

DB 인덱스도 같은 역할을 한다.

---

## 2. 인덱스가 없는 경우

예를 들어 사용자 1,000만 명이 있다고 하자.

```sql
SELECT *
FROM users
WHERE email = 'a@example.com';
```

email 인덱스가 없다면 많은 경우 테이블을 처음부터 끝까지 확인해야 한다.

```text
Row 1 확인
Row 2 확인
Row 3 확인
...
Row 10,000,000 확인
```

이를 **Full Table Scan**이라고 한다.

---

## 3. 인덱스가 있는 경우

```text
email index
        ↓
a@example.com
        ↓
해당 레코드 위치
```

전체 테이블을 모두 읽지 않고 위치를 빠르게 찾을 수 있다.

---

## 4. 장점

- SELECT 성능 향상
- WHERE 조건 검색 성능 향상
- JOIN 성능 향상 가능
- ORDER BY 최적화 가능
- GROUP BY 최적화 가능
- 범위 검색에 유리

---

## 5. 단점

인덱스는 공짜가 아니다.

```text
조회 성능 ↑
쓰기 비용 ↑
저장 공간 ↑
```

### INSERT
데이터 추가 시 인덱스에도 새로운 키를 추가해야 한다.

### UPDATE
인덱스 대상 컬럼 값이 바뀌면 인덱스도 수정해야 한다.

### DELETE
데이터 삭제 시 인덱스에서도 제거해야 한다.

따라서 조회가 거의 없는 컬럼에 무분별하게 인덱스를 만들면 오히려 손해일 수 있다.

---

# 4.5.2 B-트리

## 1. 왜 B-트리를 사용하는가?

DB는 메모리 접근보다 디스크/SSD I/O 비용이 훨씬 크다.

일반 이진 탐색 트리는 노드 하나에 적은 값만 저장하기 때문에 트리가 깊어질 수 있다.

B-트리는 하나의 노드에 여러 키를 저장한다.

```text
         [20 | 40]
        /    |    \
      <20  20~40   >40
```

그래서 트리 높이를 낮추고 저장장치 접근 횟수를 줄일 수 있다.

---

## 2. B-트리 특징

- 균형 트리
- 모든 리프가 비슷한 깊이를 유지
- 하나의 노드에 여러 키 저장
- 탐색/삽입/삭제가 대략 O(log N)
- 디스크 기반 데이터 저장에 적합

---

## 3. B+Tree

실제 관계형 DB 인덱스에서는 **B+Tree 계열**이 많이 사용된다.

특징:

- 내부 노드는 탐색용 키 중심
- 실제 레코드 위치 정보는 리프 노드에 저장
- 리프 노드끼리 순서대로 연결

```text
             [30 | 60]
            /    |    \
           /     |     \
 [10,20] → [30,40,50] → [60,70,80]
```

이 구조 때문에 범위 검색에 강하다.

---

## 4. 범위 검색 예시

```sql
SELECT *
FROM products
WHERE price BETWEEN 10000 AND 50000;
```

B+Tree에서는:

```text
10000 위치 찾기
↓
리프 노드를 순차적으로 따라감
↓
50000까지 읽기
```

따라서 다음 연산과 잘 맞는다.

```text
=
>
>=
<
<=
BETWEEN
ORDER BY
```

---

## 5. Hash Index와 비교

Hash Index는 정확한 값 검색에 강하다.

```sql
WHERE id = 100
```

반면 다음과 같은 범위 검색에는 적합하지 않다.

```sql
WHERE id > 100
ORDER BY id
```

B+Tree는 키가 정렬되어 있기 때문에 범위 검색에 유리하다.

---

# 4.5.3 인덱스 만드는 방법

## 1. 기본 인덱스

```sql
CREATE INDEX idx_users_email
ON users(email);
```

---

## 2. UNIQUE 인덱스

```sql
CREATE UNIQUE INDEX idx_users_email
ON users(email);
```

중복 값을 허용하지 않는다.

---

## 3. 복합 인덱스

여러 컬럼을 묶어 하나의 인덱스로 만든다.

```sql
CREATE INDEX idx_orders_member_date
ON orders(member_id, order_date);
```

복합 인덱스는 **컬럼의 순서가 매우 중요**하다.

---

## 4. 복합 인덱스의 왼쪽 우선 특성

인덱스가 다음과 같다고 하자.

```text
(member_id, order_date)
```

다음 쿼리는 잘 활용할 수 있다.

```sql
WHERE member_id = 10;
```

```sql
WHERE member_id = 10
  AND order_date >= '2026-01-01';
```

하지만:

```sql
WHERE order_date >= '2026-01-01';
```

처럼 첫 번째 컬럼을 사용하지 않으면 효율적으로 활용되지 않을 수 있다.

개념적으로:

```text
(A, B, C) 인덱스

A              가능
A, B           가능
A, B, C        가능

B만 사용       불리할 수 있음
C만 사용       불리할 수 있음
```

DBMS와 쿼리 형태에 따라 실제 동작은 달라질 수 있으므로 실행 계획으로 확인해야 한다.

---

## 5. 인덱스 후보 컬럼

주로 다음 컬럼을 고려한다.

- WHERE 조건에 자주 등장
- JOIN 조건에 자주 등장
- ORDER BY에 자주 등장
- GROUP BY에 자주 등장
- 선택도(Selectivity)가 높은 컬럼

---

## 6. 선택도

선택도는 컬럼 값이 데이터를 얼마나 잘 구분하는지를 나타낸다.

예:

```text
이메일
주민번호
사용자 ID
```

는 대부분 값이 다르므로 선택도가 높다.

반면:

```text
성별
활성 여부
결제 여부
```

처럼 값의 종류가 매우 적으면 선택도가 낮다.

선택도가 매우 낮은 컬럼은 단독 인덱스의 효과가 작을 수 있다.

---

# 4.5.4 인덱스 최적화 기법

## 1. 모든 컬럼에 인덱스를 만들지 않는다

인덱스가 많아질수록:

```text
INSERT
UPDATE
DELETE
```

비용이 커진다.

따라서 **실제 조회 패턴**을 보고 만든다.

---

## 2. 자주 실행되는 쿼리를 먼저 본다

예:

```sql
SELECT *
FROM orders
WHERE member_id = ?
  AND status = ?
  AND created_at >= ?;
```

이 쿼리가 매우 자주 실행된다면 복합 인덱스를 검토할 수 있다.

```text
(member_id, status, created_at)
```

다만 실제 컬럼 순서는:

- 조건 형태
- 선택도
- 정렬 여부
- 범위 검색 여부

를 함께 봐야 한다.

---

## 3. 인덱스 컬럼에 함수 사용 주의

예:

```sql
WHERE YEAR(created_at) = 2026;
```

이런 형태는 일반 인덱스를 효율적으로 사용하지 못할 수 있다.

가능하면:

```sql
WHERE created_at >= '2026-01-01'
  AND created_at < '2027-01-01';
```

처럼 범위 조건으로 바꾸는 것이 유리할 수 있다.

---

## 4. LIKE 검색 주의

다음은 일반 B-Tree 인덱스를 활용할 수 있는 경우가 많다.

```sql
WHERE name LIKE 'Kim%';
```

반면:

```sql
WHERE name LIKE '%Kim';
```

은 시작 부분을 알 수 없어 인덱스를 활용하기 어렵다.

```text
'Kim%'
→ Kim으로 시작하는 위치를 찾으면 됨

'%Kim'
→ 어디서 시작해야 할지 알 수 없음
```

---

## 5. Covering Index

쿼리에 필요한 컬럼을 인덱스가 모두 가지고 있다면 테이블 본문을 다시 읽지 않고 인덱스만으로 결과를 반환할 수 있다.

예:

```sql
SELECT member_id, order_date
FROM orders
WHERE member_id = 10;
```

인덱스:

```text
(member_id, order_date)
```

라면 Covering Index가 될 수 있다.

---

## 6. Clustered Index

데이터 저장 순서가 특정 인덱스 구조와 강하게 연결되어 있는 형태다.

예를 들어 MySQL InnoDB에서는 기본 키가 클러스터드 인덱스 역할을 한다.

특징:

- 기본 키 범위 조회에 유리
- 데이터가 기본 키 기준으로 구성됨
- 한 테이블에 사실상 하나의 클러스터링 순서만 존재

---

## 7. Secondary Index

기본 키가 아닌 컬럼에 만든 보조 인덱스다.

예:

```text
PRIMARY KEY
→ user_id

Secondary Index
→ email
```

InnoDB에서는 보조 인덱스 리프에 기본 키 값이 저장되고,
필요한 경우 기본 키 인덱스를 다시 찾아가는 구조를 사용할 수 있다.

---

## 8. 인덱스가 있어도 사용되지 않을 수 있음

예:

```sql
SELECT *
FROM users
WHERE gender = 'M';
```

전체 데이터의 절반이 `M`이라면 인덱스를 통해 수많은 레코드를 다시 찾는 것보다 Full Table Scan이 더 빠를 수 있다.

따라서:

```text
인덱스 존재
≠
항상 인덱스 사용
```

이다.

옵티마이저가 예상 비용을 계산해 실행 방법을 결정한다.

---

## 9. 실행 계획 확인

인덱스 최적화에서는 실행 계획을 확인하는 것이 중요하다.

MySQL:

```sql
EXPLAIN
SELECT *
FROM orders
WHERE member_id = 10;
```

확인할 내용:

- 어떤 인덱스를 사용하는가
- 예상 조회 행 수
- Full Table Scan인가
- JOIN 순서는 어떤가
- 별도 정렬이 발생하는가

---

# 실전 예제

다음 쿼리가 매우 자주 실행된다고 해보자.

```sql
SELECT order_id, created_at, amount
FROM orders
WHERE member_id = 100
  AND created_at >= '2026-01-01'
ORDER BY created_at DESC;
```

좋은 인덱스 후보:

```sql
CREATE INDEX idx_orders_member_created
ON orders(member_id, created_at);
```

이유:

```text
member_id
→ 동등 조건 검색

created_at
→ 범위 검색 + 정렬에 활용 가능
```

---

# 인덱스가 효과적이지 않을 수 있는 경우

- 테이블이 매우 작음
- 대부분의 행을 조회함
- INSERT/UPDATE/DELETE가 매우 빈번함
- 선택도가 매우 낮은 컬럼
- 실제 조회 조건에 거의 등장하지 않는 컬럼

---

# 면접 질문

## Q1. 인덱스를 사용하는 이유는?
전체 테이블을 탐색하지 않고 필요한 데이터의 위치를 빠르게 찾기 위해 사용한다. 대신 저장 공간과 쓰기 비용이 증가한다.

## Q2. 왜 B+Tree를 많이 사용하나요?
트리 높이가 낮아 저장장치 접근 횟수를 줄일 수 있고, 리프 노드가 정렬 및 연결되어 있어 단일 값 조회뿐 아니라 범위 검색에도 유리하기 때문이다.

## Q3. 인덱스를 많이 만들면 좋은가요?
아니다. 인덱스마다 저장 공간이 필요하고 INSERT, UPDATE, DELETE 때 함께 관리해야 하므로 쓰기 성능이 떨어질 수 있다.

## Q4. 복합 인덱스에서 컬럼 순서가 중요한 이유는?
B-Tree 계열 인덱스는 앞쪽 컬럼부터 정렬되므로 선두 컬럼을 기준으로 검색해야 뒤의 컬럼도 효율적으로 활용하기 쉽기 때문이다.

## Q5. 인덱스가 있는데도 Full Table Scan을 할 수 있나요?
가능하다. 옵티마이저가 인덱스를 이용하는 비용보다 전체 테이블을 읽는 비용이 더 낮다고 판단하면 인덱스를 사용하지 않을 수 있다.

---

# 핵심 요약

```text
인덱스
= 검색 속도를 높이기 위한 추가 자료구조

장점
= SELECT 성능 향상

단점
= 저장 공간 + 쓰기 비용 증가

B+Tree
= 범위 검색에 강함

복합 인덱스
= 컬럼 순서 중요

인덱스 최적화
= 실제 쿼리 패턴 + 선택도 + 실행 계획을 보고 결정
```
