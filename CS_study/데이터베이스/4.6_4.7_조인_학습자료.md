# 4.6 조인의 종류

조인(Join)은 **두 개 이상의 테이블을 특정 컬럼을 기준으로 연결하여 데이터를 조회하는 연산**이다.

예시 테이블

### `users`

| user_id | name |
|---|---|
| 1 | Kim |
| 2 | Lee |
| 3 | Park |

### `orders`

| order_id | user_id | product |
|---|---|---|
| 101 | 1 | Laptop |
| 102 | 1 | Mouse |
| 103 | 2 | Keyboard |
| 104 | 4 | Monitor |

---

## 4.6.1 내부 조인 (INNER JOIN)

두 테이블에서 **조인 조건을 만족하는 데이터만 조회**한다.

```sql
SELECT *
FROM users u
INNER JOIN orders o
ON u.user_id = o.user_id;
```

결과

| user_id | name | order_id | product |
|---|---|---|---|
| 1 | Kim | 101 | Laptop |
| 1 | Kim | 102 | Mouse |
| 2 | Lee | 103 | Keyboard |

특징

- 양쪽 테이블에 모두 존재하는 데이터만 조회
- 가장 많이 사용되는 조인
- 조건에 맞지 않는 행은 제외됨

```text
A       B

┌───┐ ┌───┐
│   ├─┤   │
└───┘ └───┘
     ↑
  공통 부분
```

즉,

```text
A ∩ B
```

---

## 4.6.2 왼쪽 조인 (LEFT JOIN)

**왼쪽 테이블의 모든 데이터**를 유지하고, 오른쪽 테이블에서 조건이 맞는 데이터를 붙인다.

조건에 맞는 데이터가 없으면 `NULL`.

```sql
SELECT *
FROM users u
LEFT JOIN orders o
ON u.user_id = o.user_id;
```

결과

| user_id | name | order_id | product |
|---|---|---|---|
| 1 | Kim | 101 | Laptop |
| 1 | Kim | 102 | Mouse |
| 2 | Lee | 103 | Keyboard |
| 3 | Park | NULL | NULL |

핵심

```text
LEFT JOIN
= 왼쪽 테이블은 무조건 유지
```

사용 예시

- 주문하지 않은 회원까지 조회
- 게시글이 없는 사용자 조회
- 매출이 없는 상품까지 조회

예를 들어 주문하지 않은 사용자만 찾으려면

```sql
SELECT u.*
FROM users u
LEFT JOIN orders o
ON u.user_id = o.user_id
WHERE o.user_id IS NULL;
```

---

## 4.6.3 오른쪽 조인 (RIGHT JOIN)

**오른쪽 테이블의 모든 데이터**를 유지하고, 왼쪽 테이블에서 조건에 맞는 데이터를 붙인다.

```sql
SELECT *
FROM users u
RIGHT JOIN orders o
ON u.user_id = o.user_id;
```

결과

| user_id | name | order_id | product |
|---|---|---|---|
| 1 | Kim | 101 | Laptop |
| 1 | Kim | 102 | Mouse |
| 2 | Lee | 103 | Keyboard |
| 4 | NULL | 104 | Monitor |

핵심

```text
RIGHT JOIN
= 오른쪽 테이블은 무조건 유지
```

실무에서는 `RIGHT JOIN`보다 테이블 순서를 바꿔 `LEFT JOIN`으로 표현하는 경우가 많다.

```sql
orders
LEFT JOIN users
```

와

```sql
users
RIGHT JOIN orders
```

는 동일한 의미가 될 수 있다.

---

## 4.6.4 합집합 조인 (FULL OUTER JOIN)

두 테이블의 **모든 데이터**를 조회한다.

조인 조건이 맞으면 합치고, 맞지 않는 데이터는 반대쪽 컬럼에 `NULL`이 들어간다.

```sql
SELECT *
FROM users u
FULL OUTER JOIN orders o
ON u.user_id = o.user_id;
```

개념적으로

```text
A ∪ B
```

결과

| user_id | name | order_id | product |
|---|---|---|---|
| 1 | Kim | 101 | Laptop |
| 1 | Kim | 102 | Mouse |
| 2 | Lee | 103 | Keyboard |
| 3 | Park | NULL | NULL |
| 4 | NULL | 104 | Monitor |

주의

MySQL은 `FULL OUTER JOIN`을 직접 지원하지 않는다.

따라서 보통

```sql
LEFT JOIN
UNION
RIGHT JOIN
```

형태로 구현한다.

```sql
SELECT *
FROM users u
LEFT JOIN orders o
ON u.user_id = o.user_id

UNION

SELECT *
FROM users u
RIGHT JOIN orders o
ON u.user_id = o.user_id;
```

---

# 조인 종류 한 번에 정리

```text
INNER JOIN
→ 양쪽에 모두 있는 데이터

LEFT JOIN
→ 왼쪽 전체 + 오른쪽 일치 데이터

RIGHT JOIN
→ 오른쪽 전체 + 왼쪽 일치 데이터

FULL OUTER JOIN
→ 양쪽 전체
```

| JOIN | 기준 |
|---|---|
| INNER JOIN | 양쪽 모두 존재 |
| LEFT JOIN | 왼쪽 전체 |
| RIGHT JOIN | 오른쪽 전체 |
| FULL OUTER JOIN | 양쪽 전체 |

---

# 4.7 조인의 원리

앞에서 본

```text
INNER JOIN
LEFT JOIN
RIGHT JOIN
```

등은 **SQL에서 어떤 결과를 원하는지**를 나타낸다.

반면 DBMS 내부에서는 실제로 두 테이블을 합치기 위해 여러 알고리즘을 사용할 수 있다.

대표적으로

```text
Nested Loop Join
Sort Merge Join
Hash Join
```

이 존재한다.

즉,

```text
SQL

SELECT *
FROM A
JOIN B
ON A.id = B.id;

        ↓

DB Optimizer

        ↓

Nested Loop Join
or
Sort Merge Join
or
Hash Join
```

실제 어떤 알고리즘을 사용할지는 **옵티마이저(Optimizer)**가 판단한다.

---

# 4.7.1 중첩 루프 조인
## Nested Loop Join

한 테이블의 행을 하나씩 읽으면서 다른 테이블에서 조건에 맞는 행을 찾는 방식.

프로그래밍으로 보면 이중 반복문과 비슷하다.

```python
for a in A:
    for b in B:
        if a.id == b.id:
            join(a, b)
```

예를 들어

```text
A
1
2
3

B
1
2
4
```

처리 과정

```text
A의 1
 → B의 1 비교 O
 → B의 2 비교
 → B의 4 비교

A의 2
 → B의 1 비교
 → B의 2 비교 O
 → B의 4 비교

A의 3
 → B 전체 비교
```

단순하게 수행하면 시간복잡도는

```text
O(N × M)
```

이다.

---

## 인덱스를 사용하는 Nested Loop Join

실제로는 내부 테이블에 인덱스가 있다면 훨씬 효율적으로 수행할 수 있다.

```text
Outer Table
    ↓
한 행 선택
    ↓
Inner Table의 Index 탐색
```

예를 들어 B의 `id`에 B-Tree 인덱스가 있으면

```text
A 행 하나
   ↓
B-Tree 탐색
   ↓
일치 데이터 조회
```

대략

```text
O(N log M)
```

형태로 수행될 수 있다.

이 방식을 흔히

```text
Index Nested Loop Join
```

이라고 한다.

---

## 특징

장점

- 구현이 단순
- 작은 테이블 조인에 유리
- 인덱스를 잘 활용하면 매우 빠름

단점

- 두 테이블이 모두 크고 인덱스가 없다면 느림
- 반복적인 랜덤 접근 발생 가능

적합한 경우

```text
Outer Table이 작음
+
Inner Table 조인 컬럼에 Index 존재
```

---

# 4.7.2 정렬 병합 조인
## Sort Merge Join

두 테이블을 **조인 키 기준으로 정렬한 뒤**, 순서대로 비교하면서 조인하는 방식이다.

예시

```text
A

1
3
5
7

B

1
2
3
5
```

두 포인터처럼 이동한다.

```text
A → 1
B → 1

같음
→ JOIN

A → 3
B → 2

2 < 3
→ B 이동

A → 3
B → 3

같음
→ JOIN
```

알고리즘 형태

```text
i = 0
j = 0

while i < N and j < M:

    if A[i] == B[j]:
        JOIN

    elif A[i] < B[j]:
        i++

    else:
        j++
```

---

## 수행 과정

```text
Table A
   ↓
Sort

Table B
   ↓
Sort

정렬된 A + 정렬된 B
        ↓
Merge
```

정렬 비용이 필요하므로 대략

```text
O(N log N + M log M)
```

이 소요된다.

이미 정렬되어 있다면 병합 과정은

```text
O(N + M)
```

에 가능하다.

---

## 특징

장점

- 대량 데이터 조인에 유리
- 순차 접근이 가능
- 범위 조건 조인에도 사용 가능

예

```sql
A.value > B.value
```

단점

- 데이터가 정렬되어 있지 않으면 정렬 비용 발생
- 메모리가 부족하면 디스크 정렬 필요

적합한 경우

```text
두 테이블 모두 큼
+
조인 키 기준 정렬이 가능
```

---

# 4.7.3 해시 조인
## Hash Join

한 테이블의 조인 키를 이용하여 **Hash Table을 만든 후**, 다른 테이블의 데이터를 해시 테이블에서 검색하는 방식.

보통 작은 테이블로 Hash Table을 만든다.

예시

```text
A

id
1
3
5
```

A를 Hash Table로 생성

```text
Hash Table

1 → A[1]
3 → A[3]
5 → A[5]
```

B를 순회

```text
B

1
2
3
5
```

각 값에 대해

```text
hash(1)
→ 존재
→ JOIN

hash(2)
→ 없음

hash(3)
→ 존재
→ JOIN
```

---

## 수행 단계

해시 조인은 크게 두 단계로 나뉜다.

### Build Phase

작은 테이블을 Hash Table로 만든다.

```text
Small Table
     ↓
Hash Function
     ↓
Hash Table
```

### Probe Phase

큰 테이블을 순회하면서 Hash Table을 조회한다.

```text
Large Table
     ↓
Hash Key
     ↓
Hash Table 검색
```

따라서 이상적인 경우 시간복잡도는

```text
O(N + M)
```

이다.

---

## 특징

장점

- 동등 조건 조인에서 매우 빠름
- 인덱스가 없어도 좋은 성능
- 대량 데이터 처리에 유리

단점

- Hash Table을 저장할 메모리 필요
- `=`, 즉 동등 비교에 주로 사용
- 범위 조건에는 적합하지 않음

예를 들어

```sql
A.id = B.id
```

에는 적합하지만

```sql
A.id > B.id
```

같은 조건에는 해시 조인을 사용할 수 없다.

---

# Build / Probe 기억하기

```text
작은 Table
   ↓
BUILD
   ↓
Hash Table 생성

큰 Table
   ↓
PROBE
   ↓
Hash Table 검색
```

일반적으로 작은 테이블을 Build 쪽으로 사용하는 이유는

```text
Hash Table 크기 감소
→ 메모리 사용량 감소
```

때문이다.

---

# 세 조인 알고리즘 비교

| 알고리즘 | 기본 원리 | 대략적 비용 | 특징 |
|---|---|---:|---|
| Nested Loop Join | 반복 비교 | O(N×M) | 작은 테이블 + 인덱스 |
| Sort Merge Join | 정렬 후 병합 | O(N log N + M log M) | 대량/정렬 데이터 |
| Hash Join | Hash Table 검색 | O(N+M) | 동등 조인에 강함 |

---

# 어떤 조인을 선택할까?

```text
Small Table + Index
        ↓
Nested Loop Join

Large Sorted Table
        ↓
Sort Merge Join

Large Table + Equality Join
        ↓
Hash Join
```

하지만 실제 SQL에서는 개발자가 직접 선택하기보다 DBMS의 **옵티마이저가 실행 계획을 생성**한다.

옵티마이저는 다음과 같은 요소를 고려한다.

```text
테이블 크기
인덱스 존재 여부
조인 조건
데이터 분포
통계 정보
메모리
정렬 여부
```

---

# JOIN 종류와 JOIN 알고리즘은 다르다

면접에서 자주 헷갈리는 부분.

### JOIN 종류

```text
INNER JOIN
LEFT JOIN
RIGHT JOIN
FULL OUTER JOIN
```

→ **어떤 데이터를 결과에 포함할 것인가**

### JOIN 알고리즘

```text
Nested Loop Join
Sort Merge Join
Hash Join
```

→ **DBMS가 실제로 데이터를 어떻게 찾을 것인가**

따라서

```text
INNER JOIN
```

을 수행한다고 해서 반드시 특정 알고리즘을 사용하는 것은 아니다.

```text
INNER JOIN

→ Nested Loop Join
→ Sort Merge Join
→ Hash Join
```

중 옵티마이저가 적절한 방식을 선택할 수 있다.

# 면접 핵심 정리

```text
Q. INNER JOIN과 LEFT JOIN 차이?

INNER JOIN
→ 양쪽 모두 조인 조건을 만족하는 행만 반환

LEFT JOIN
→ 왼쪽 테이블의 모든 행을 유지하고
   오른쪽에 일치하는 값이 없으면 NULL
```

```text
Q. Nested Loop Join은 언제 좋은가?

Outer Table이 작고
Inner Table의 조인 컬럼에 Index가 있을 때.
```

```text
Q. Hash Join은 언제 좋은가?

대량 데이터의 Equality Join에서 유리.
한 테이블로 Hash Table을 만들고
다른 테이블이 이를 Probe.
```

```text
Q. Hash Join이 범위 검색에 불리한 이유?

Hash Table은
정확한 Key 탐색에는 빠르지만

>, <, BETWEEN

등 Key의 순서 정보를 이용할 수 없기 때문.
```

```text
Q. Sort Merge Join의 장점?

두 테이블이 이미 정렬되어 있다면
O(N + M)에 병합 가능하며

대용량 데이터 및 범위 조인에 유리.
```

# 최종 요약

```text
JOIN 종류
──────────────────────

INNER
→ 공통 데이터

LEFT
→ 왼쪽 전체

RIGHT
→ 오른쪽 전체

FULL OUTER
→ 양쪽 전체


JOIN 알고리즘
──────────────────────

Nested Loop
→ 반복 탐색
→ 작은 테이블 + Index

Sort Merge
→ 정렬 후 Two Pointer 방식 병합
→ 대용량 / 정렬 데이터

Hash
→ Hash Table Build + Probe
→ Equality Join에 강함
→ 평균 O(N + M)
```
