# 3.3 프로세스와 스레드

> 운영체제에서 **프로세스는 실행 중인 프로그램**, **스레드는 프로세스 안에서 실제 작업을 수행하는 실행 흐름**이다.  
> 프로세스와 스레드를 이해하려면 프로그램이 어떻게 실행 파일로 만들어지고, 메모리에 적재되며, CPU를 할당받는지부터 살펴봐야 한다.

---

## 3.3.1 프로세스와 컴파일 과정

### 1. 프로그램과 프로세스

- **프로그램(Program)**
  - 저장 장치에 존재하는 실행 파일
  - 아직 실행되지 않은 정적인 상태
  - 예: `chrome.exe`, `python`, `a.out`

- **프로세스(Process)**
  - 프로그램이 메모리에 적재되어 실행 중인 상태
  - CPU 실행 정보, 메모리, 열린 파일, 상태 정보 등을 포함
  - 같은 프로그램을 여러 번 실행하면 서로 다른 프로세스가 생성됨

```text
프로그램 실행
    ↓
운영체제가 메모리 공간 할당
    ↓
프로그램 코드와 데이터를 메모리에 적재
    ↓
PCB 생성
    ↓
프로세스 실행
```

### 2. 소스 코드가 실행 파일이 되는 과정

C/C++ 계열 언어는 일반적으로 다음 과정을 거친다.

```text
소스 코드
   ↓ 전처리
전처리된 소스 코드
   ↓ 컴파일
어셈블리 코드
   ↓ 어셈블
목적 파일
   ↓ 링크
실행 파일
   ↓ 로더
메모리에 적재된 프로세스
```

### 3. 전처리(Preprocessing)

전처리기는 컴파일 전에 소스 코드를 정리한다.

주요 작업:

- `#include`에 지정된 헤더 파일 삽입
- `#define` 매크로 치환
- 조건부 컴파일 처리
- 주석 제거

```c
#define MAX 100

int arr[MAX];
```

전처리 후에는 `MAX`가 `100`으로 치환된다.

### 4. 컴파일(Compilation)

고급 언어로 작성된 코드를 어셈블리어로 변환한다.

컴파일 과정에서는 다음 작업도 수행된다.

- 문법 검사
- 타입 검사
- 코드 최적화
- 중간 표현 생성
- 어셈블리 코드 생성

```text
C 코드 → 어셈블리 코드
```

### 5. 어셈블(Assembly)

어셈블리 코드를 기계어로 변환하여 **목적 파일(Object File)**을 생성한다.

목적 파일에는 기계어 코드가 있지만, 외부 함수나 라이브러리의 실제 주소가 아직 확정되지 않을 수 있다.

```text
main.c → main.o
util.c → util.o
```

### 6. 링크(Linking)

여러 목적 파일과 라이브러리를 결합하여 실행 파일을 만든다.

```text
main.o + util.o + 표준 라이브러리 → 실행 파일
```

#### 정적 링크

필요한 라이브러리 코드를 실행 파일 안에 포함한다.

장점:

- 실행 시 외부 라이브러리에 대한 의존성이 적음
- 배포가 비교적 간단함

단점:

- 실행 파일 크기가 커짐
- 라이브러리가 수정되면 다시 빌드해야 함

#### 동적 링크

실행 시점에 외부 공유 라이브러리를 연결한다.

예:

- Windows: `.dll`
- Linux: `.so`
- macOS: `.dylib`

장점:

- 실행 파일 크기가 작음
- 여러 프로세스가 라이브러리 코드를 공유할 수 있음

단점:

- 필요한 라이브러리가 없거나 버전이 맞지 않으면 실행 오류 발생

### 7. 로딩(Loading)

로더가 실행 파일을 메모리에 적재한다.

주요 작업:

- 프로세스 주소 공간 생성
- 코드와 데이터를 메모리에 배치
- 스택과 힙 초기화
- 동적 라이브러리 연결
- 프로그램 시작 지점으로 이동

### 핵심 정리

```text
프로그램 = 저장 장치에 있는 실행 파일
프로세스 = 메모리에 올라와 실행 중인 프로그램
컴파일 = 고급 언어를 저수준 코드로 변환
링크 = 목적 파일과 라이브러리를 결합
로드 = 실행 파일을 메모리에 적재
```

## 3.3.2 프로세스의 상태

프로세스는 항상 CPU에서 실행되는 것이 아니다. CPU를 기다리거나 입출력 작업이 끝나기를 기다리는 등 여러 상태를 이동한다.

### 1. 기본 프로세스 상태

| 상태 | 의미 |
|---|---|
| 생성(New) | 프로세스가 생성되는 중 |
| 준비(Ready) | CPU만 할당받으면 실행 가능한 상태 |
| 실행(Running) | CPU를 할당받아 명령어를 실행 중 |
| 대기/블록(Waiting/Blocked) | 입출력이나 특정 이벤트를 기다리는 상태 |
| 종료(Terminated) | 실행이 끝난 상태 |

### 2. 상태 전이

```text
                CPU 할당
      ┌────────────────────────┐
      │                        ▼
[생성] ── 승인 ──> [준비] ──> [실행] ──> [종료]
                    ▲            │
                    │            │ 입출력 요청
        타임 슬라이스 종료      ▼
                    └──────── [대기]
                                 │
                                 │ 입출력 완료
                                 └──────> [준비]
```

### 3. 준비 상태와 대기 상태의 차이

#### 준비 상태

- 실행에 필요한 조건은 모두 만족
- CPU만 기다리는 상태
- 준비 큐에 들어감

#### 대기 상태

- CPU를 받아도 바로 실행할 수 없음
- 입출력 완료, 락 해제, 네트워크 응답 등 특정 사건을 기다림

```text
준비: "CPU만 주면 실행할 수 있음"
대기: "CPU를 줘도 아직 실행할 수 없음"
```

### 4. 디스패치와 선점

- **디스패치(Dispatch)**
  - 준비 상태의 프로세스에 CPU를 할당하는 작업

- **선점(Preemption)**
  - 실행 중인 프로세스에서 CPU를 강제로 회수하는 것
  - 타임 슬라이스 만료, 우선순위가 높은 프로세스 등장 등으로 발생

### 5. 보류 상태

일부 운영체제 설명에서는 메모리 부족으로 프로세스가 디스크의 스왑 영역으로 이동한 상태를 추가한다.

- 준비 보류(Ready Suspended)
- 대기 보류(Blocked Suspended)

보류 상태에서는 프로세스가 메인 메모리 밖에 있기 때문에 바로 실행할 수 없다.

### 6. 문맥 교환(Context Switch)

CPU가 실행할 프로세스를 변경할 때 기존 프로세스의 실행 정보를 저장하고, 새로운 프로세스의 실행 정보를 복원하는 과정이다.

저장되는 정보의 예:

- 프로그램 카운터
- CPU 레지스터
- 스택 포인터
- 프로세스 상태
- 메모리 관리 정보

```text
프로세스 A 실행
   ↓ 인터럽트 또는 스케줄링
A의 CPU 상태를 PCB에 저장
   ↓
B의 PCB에서 CPU 상태 복원
   ↓
프로세스 B 실행
```

문맥 교환 중에는 실제 사용자 작업이 수행되지 않으므로 오버헤드가 발생한다.

## 3.3.3 프로세스의 메모리 구조

프로세스는 운영체제로부터 독립적인 가상 주소 공간을 할당받는다.

일반적인 메모리 구조는 다음과 같다.

```text
높은 주소
┌──────────────────────────────┐
│ Stack                        │
│ 지역 변수, 매개변수, 반환 주소 │
│            ↓                 │
├──────────────────────────────┤
│                              │
│ 사용되지 않은 공간             │
│                              │
├──────────────────────────────┤
│            ↑                 │
│ Heap                         │
│ 동적 할당 메모리               │
├──────────────────────────────┤
│ BSS                          │
│ 초기화되지 않은 전역/정적 변수   │
├──────────────────────────────┤
│ Data                         │
│ 초기화된 전역/정적 변수         │
├──────────────────────────────┤
│ Text(Code)                   │
│ 실행 명령어, 상수              │
└──────────────────────────────┘
낮은 주소
```

> 실제 배치 방향과 세부 구조는 운영체제, CPU 아키텍처, 실행 파일 형식에 따라 달라질 수 있다.

### 1. 코드 영역(Text Segment)

- 실행할 기계어 명령어 저장
- 일반적으로 읽기 전용
- 여러 프로세스가 같은 프로그램을 실행할 경우 물리 메모리의 코드 페이지를 공유할 수 있음

```c
int add(int a, int b) {
    return a + b;
}
```

함수의 기계어 명령어가 코드 영역에 저장된다.

### 2. 데이터 영역(Data Segment)

초기값이 있는 전역 변수와 정적 변수가 저장된다.

```c
int global_count = 10;
static int limit = 100;
```

프로그램 시작 시 할당되고, 프로세스 종료 시 해제된다.

### 3. BSS 영역

초기화되지 않았거나 0으로 초기화된 전역 변수와 정적 변수가 저장된다.

```c
int global_value;
static int count;
```

실행 파일에 모든 0 데이터를 직접 저장하지 않고, 필요한 크기 정보만 기록할 수 있어 파일 크기를 줄일 수 있다.

### 4. 힙 영역(Heap)

동적 메모리 할당에 사용된다.

```c
int* arr = malloc(sizeof(int) * 100);
```

Python에서는 객체 대부분이 힙에 생성되며, 메모리 관리는 런타임과 가비지 컬렉터가 담당한다.

특징:

- 실행 중 크기를 결정할 수 있음
- 명시적으로 해제하거나 가비지 컬렉션 필요
- 과도한 할당과 해제는 단편화를 일으킬 수 있음
- 일반적으로 낮은 주소에서 높은 주소 방향으로 증가

### 5. 스택 영역(Stack)

함수 호출에 필요한 정보가 저장된다.

주요 내용:

- 함수 매개변수
- 지역 변수
- 반환 주소
- 이전 스택 프레임 정보
- 일부 레지스터 값

```c
void func(int x) {
    int y = 10;
}
```

`x`, `y`, 반환 주소 등이 스택 프레임에 저장될 수 있다.

특징:

- 함수 호출 시 스택 프레임 생성
- 함수 종료 시 자동 해제
- 접근 속도가 빠름
- 크기가 제한적
- 깊은 재귀 호출이나 큰 지역 배열로 스택 오버플로가 발생할 수 있음

### 6. 스택과 힙 비교

| 구분 | 스택 | 힙 |
|---|---|---|
| 용도 | 함수 호출, 지역 변수 | 동적 메모리 |
| 할당 시점 | 함수 호출 과정 | 실행 중 요청 |
| 해제 | 함수 종료 시 자동 | 직접 해제 또는 GC |
| 속도 | 일반적으로 빠름 | 상대적으로 느림 |
| 크기 | 비교적 작음 | 비교적 큼 |
| 주요 문제 | 스택 오버플로 | 메모리 누수, 단편화 |

### 7. 가상 메모리 관점

각 프로세스는 자신만의 독립된 가상 주소 공간을 가진 것처럼 동작한다.

```text
프로세스 A의 0x1000 ─┐
                     ├─ 서로 다른 물리 메모리 페이지로 매핑 가능
프로세스 B의 0x1000 ─┘
```

장점:

- 프로세스 간 메모리 격리
- 보안과 안정성 향상
- 실제 물리 메모리보다 큰 주소 공간 사용 가능
- 공유 라이브러리나 공유 메모리 페이지는 선택적으로 공유 가능

## 3.3.4 PCB

### 1. PCB란?

**PCB(Process Control Block)**는 운영체제가 프로세스를 관리하기 위해 유지하는 자료구조다.

프로세스마다 하나의 PCB가 존재하며, 커널 영역에 저장된다.

```text
프로세스 = 실행 중인 작업
PCB = 운영체제가 그 프로세스를 관리하기 위한 기록표
```

### 2. PCB에 저장되는 정보

| 정보 | 설명 |
|---|---|
| 프로세스 식별자 | PID, 부모 PID 등 |
| 프로세스 상태 | 생성, 준비, 실행, 대기, 종료 |
| 프로그램 카운터 | 다음에 실행할 명령어 주소 |
| CPU 레지스터 | 문맥 교환에 필요한 레지스터 값 |
| 스케줄링 정보 | 우선순위, 큐 위치, CPU 사용량 |
| 메모리 관리 정보 | 페이지 테이블, 세그먼트 정보 |
| 입출력 상태 | 열린 파일, 사용 중인 장치 |
| 계정 정보 | 사용자 ID, 실행 시간, 권한 |
| 프로세스 관계 | 부모·자식 프로세스 정보 |

### 3. PCB와 문맥 교환

문맥 교환 시 PCB가 핵심 역할을 한다.

```text
1. 현재 프로세스의 레지스터와 프로그램 카운터를 PCB에 저장
2. 프로세스 상태를 준비 또는 대기로 변경
3. 다음 프로세스의 PCB를 선택
4. 선택된 PCB에서 실행 정보를 CPU에 복원
5. 새 프로세스 실행
```

### 4. 프로세스 테이블

운영체제는 여러 프로세스의 PCB를 관리하기 위해 프로세스 테이블을 사용한다.

```text
프로세스 테이블
├─ PCB 1: PID 100
├─ PCB 2: PID 101
├─ PCB 3: PID 102
└─ ...
```

### 5. PCB와 TCB

스레드를 지원하는 운영체제는 스레드별로 **TCB(Thread Control Block)**를 관리한다.

- PCB: 프로세스 단위 자원 정보
- TCB: 스레드 단위 실행 상태 정보

TCB에는 다음 정보가 포함될 수 있다.

- 스레드 ID
- 프로그램 카운터
- 레지스터
- 스택 포인터
- 스레드 상태
- 스케줄링 정보

## 3.3.5 멀티프로세싱

### 1. 멀티프로세싱이란?

여러 프로세스를 동시에 실행하여 작업을 처리하는 방식이다.

CPU 코어가 여러 개라면 여러 프로세스를 실제로 병렬 실행할 수 있다.

```text
프로세스 A → CPU Core 1
프로세스 B → CPU Core 2
프로세스 C → CPU Core 3
```

단일 코어에서도 운영체제가 빠르게 프로세스를 전환하면 동시에 실행되는 것처럼 보이는 동시성이 가능하다.

### 2. 동시성과 병렬성

- **동시성(Concurrency)**
  - 여러 작업이 겹치는 시간 동안 진행되는 구조
  - 하나의 코어에서도 문맥 교환으로 구현 가능

- **병렬성(Parallelism)**
  - 여러 작업이 같은 순간에 실제로 실행
  - 일반적으로 여러 CPU 코어가 필요

```text
동시성: 작업을 번갈아 처리
병렬성: 작업을 동시에 처리
```

### 3. 멀티프로세싱의 장점

- 프로세스별 메모리가 분리되어 안정성이 높음
- 한 프로세스가 비정상 종료되어도 다른 프로세스에 미치는 영향이 작음
- 여러 CPU 코어를 활용할 수 있음
- CPU 집약적 작업에서 효과적
- 언어 런타임의 스레드 제약을 피할 수 있음

예: Python의 CPython에서는 CPU 집약적 작업을 여러 코어에서 처리할 때 `multiprocessing`이 유리할 수 있다.

### 4. 멀티프로세싱의 단점

- 프로세스 생성 비용이 큼
- 프로세스마다 독립적인 메모리 공간 필요
- 문맥 교환 비용이 스레드보다 큼
- 프로세스 간 통신이 복잡함
- 데이터를 전달할 때 직렬화 비용이 발생할 수 있음

### 5. 프로세스 간 통신(IPC)

프로세스는 기본적으로 메모리를 공유하지 않으므로 IPC가 필요하다.

#### 파이프(Pipe)

- 단방향 또는 양방향 바이트 스트림
- 부모-자식 프로세스 통신에 자주 사용

#### 메시지 큐(Message Queue)

- 메시지 단위로 데이터를 전달
- 송신자와 수신자의 실행 시점을 분리할 수 있음

#### 공유 메모리(Shared Memory)

- 여러 프로세스가 같은 메모리 영역을 공유
- 복사 비용이 적어 빠름
- 동기화가 반드시 필요

#### 소켓(Socket)

- 같은 컴퓨터 또는 네트워크의 다른 컴퓨터와 통신 가능
- 분산 시스템에서 널리 사용

#### 파일

- 구현이 단순하지만 속도가 느리고 동시 접근 제어가 필요

### 6. 프로세스 생성

Unix 계열 운영체제에서는 대표적으로 `fork()`와 `exec()`를 사용한다.

- `fork()`
  - 현재 프로세스를 복제하여 자식 프로세스 생성
- `exec()`
  - 현재 프로세스의 메모리 내용을 새로운 프로그램으로 교체

```text
부모 프로세스
    │ fork()
    ├─────────> 자식 프로세스
    │              │ exec()
    │              ▼
    │         새로운 프로그램 실행
```

현대 운영체제는 `fork()` 시 메모리를 즉시 전부 복사하지 않고 **Copy-on-Write**를 사용할 수 있다.

- 부모와 자식이 같은 물리 페이지를 읽기 전용으로 공유
- 어느 한쪽이 페이지를 수정할 때 실제 복사

### 7. 좀비 프로세스와 고아 프로세스

#### 좀비 프로세스

- 자식 프로세스는 종료됐지만 부모가 종료 상태를 회수하지 않은 상태
- 실행되지는 않지만 프로세스 테이블 항목이 남아 있음

#### 고아 프로세스

- 부모 프로세스가 먼저 종료된 자식 프로세스
- Unix 계열에서는 일반적으로 시스템 프로세스가 새로운 부모 역할을 맡음

## 3.3.6 스레드와 멀티스레딩

### 1. 스레드란?

스레드는 프로세스 안에서 실제로 명령어를 실행하는 최소 실행 단위다.

하나의 프로세스는 하나 이상의 스레드를 가진다.

```text
프로세스
├─ 코드 영역       ┐
├─ 데이터 영역     │ 스레드 간 공유
├─ 힙 영역         ┘
├─ 스레드 1: PC, 레지스터, 스택
├─ 스레드 2: PC, 레지스터, 스택
└─ 스레드 3: PC, 레지스터, 스택
```

### 2. 스레드가 공유하는 것과 독립적으로 가지는 것

#### 공유하는 자원

- 코드 영역
- 데이터 영역
- 힙 영역
- 열린 파일
- 프로세스의 주소 공간
- 일부 운영체제 자원

#### 스레드별 독립 자원

- 프로그램 카운터
- CPU 레지스터
- 스택
- 스레드 ID
- 스레드 상태
- 일부 스레드 로컬 저장소

### 3. 멀티스레딩이란?

하나의 프로세스 안에서 여러 스레드가 동시에 작업하는 방식이다.

예: 웹 브라우저

- UI 스레드
- 네트워크 스레드
- 렌더링 스레드
- 파일 입출력 스레드

### 4. 멀티스레딩의 장점

- 프로세스보다 생성과 종료 비용이 작음
- 같은 메모리를 공유하므로 데이터 교환이 빠름
- 문맥 교환 비용이 상대적으로 작음
- 입출력 대기 중 다른 스레드가 작업 가능
- 응답성이 좋아짐
- 자원 사용량이 상대적으로 적음

### 5. 멀티스레딩의 단점

- 공유 자원으로 인한 경쟁 상태 발생 가능
- 동기화가 필요함
- 하나의 스레드 오류가 전체 프로세스에 영향을 줄 수 있음
- 실행 순서가 비결정적이라 디버깅이 어려움
- 교착 상태, 기아 상태, 라이브락 등이 발생할 수 있음

### 6. 프로세스와 스레드 비교

| 구분 | 프로세스 | 스레드 |
|---|---|---|
| 기본 개념 | 실행 중인 프로그램 | 프로세스 내부 실행 흐름 |
| 메모리 | 독립된 주소 공간 | 같은 프로세스 메모리 공유 |
| 생성 비용 | 큼 | 상대적으로 작음 |
| 문맥 교환 | 상대적으로 무거움 | 상대적으로 가벼움 |
| 데이터 교환 | IPC 필요 | 공유 메모리로 직접 접근 |
| 안정성 | 높은 격리성 | 한 스레드 문제가 전체에 영향 |
| 동기화 | 공유 시 필요 | 대부분 필요 |
| 적합한 작업 | 독립 작업, CPU 병렬 처리 | 입출력 병행, 빠른 자원 공유 |

### 7. 사용자 수준 스레드와 커널 수준 스레드

#### 사용자 수준 스레드

- 사용자 공간의 스레드 라이브러리가 관리
- 생성과 전환이 빠름
- 커널이 각 스레드를 직접 알지 못할 수 있음
- 하나의 스레드가 블로킹되면 전체가 멈출 수 있음

#### 커널 수준 스레드

- 운영체제 커널이 직접 관리
- 스케줄링과 병렬 실행 가능
- 생성과 전환 비용이 상대적으로 큼

### 8. Python의 스레드와 GIL

CPython에는 **GIL(Global Interpreter Lock)**이 있다.

- 한 시점에 하나의 스레드만 Python 바이트코드를 실행할 수 있도록 제한
- CPU 집약적 순수 Python 작업은 스레드를 늘려도 성능 향상이 제한적일 수 있음
- 파일, 네트워크, DB 등 입출력 대기 작업에서는 스레드가 여전히 효과적
- NumPy, PyTorch처럼 내부에서 네이티브 코드를 실행하는 라이브러리는 GIL을 해제할 수 있음

```text
I/O 집약적 작업 → 멀티스레딩 또는 비동기 처리
CPU 집약적 작업 → 멀티프로세싱 또는 네이티브 병렬 연산
```

## 3.3.7 공유 자원과 임계 영역

### 1. 공유 자원

여러 프로세스나 스레드가 함께 접근하는 자원이다.

예:

- 전역 변수
- 힙 메모리의 객체
- 파일
- 데이터베이스 레코드
- 네트워크 소켓
- 프린터
- 공유 메모리

### 2. 경쟁 상태(Race Condition)

여러 실행 흐름이 공유 자원에 동시에 접근하여 실행 순서에 따라 결과가 달라지는 문제다.

```python
count += 1
```

이 코드는 내부적으로 대략 다음 과정으로 나뉠 수 있다.

```text
1. count 값을 메모리에서 읽음
2. 읽은 값에 1을 더함
3. 결과를 count에 저장
```

두 스레드가 동시에 `count = 0`을 읽는 경우:

```text
스레드 A: count 읽기 → 0
스레드 B: count 읽기 → 0
스레드 A: 1 저장
스레드 B: 1 저장
```

기대 결과는 2지만 실제 결과는 1이 될 수 있다.

### 3. 임계 영역(Critical Section)

공유 자원에 접근하는 코드 영역이다.

한 시점에 하나의 실행 흐름만 임계 영역에 들어가도록 제한해야 한다.

```text
진입 영역
   ↓
임계 영역
   ↓
퇴장 영역
   ↓
나머지 영역
```

### 4. 임계 영역 문제의 조건

올바른 임계 영역 제어는 일반적으로 다음 조건을 만족해야 한다.

#### 상호 배제(Mutual Exclusion)

한 프로세스나 스레드가 임계 영역에 있으면 다른 실행 흐름은 들어갈 수 없어야 한다.

#### 진행(Progress)

임계 영역에 아무도 없고 진입하려는 실행 흐름이 있다면, 누가 들어갈지 결정이 무한히 미뤄지면 안 된다.

#### 한정 대기(Bounded Waiting)

임계 영역에 진입을 요청한 실행 흐름이 무한히 기다리지 않도록 대기 횟수에 한계가 있어야 한다.

### 5. 뮤텍스(Mutex)

하나의 실행 흐름만 임계 영역에 진입하게 하는 잠금 방식이다.

```text
lock 획득
   ↓
공유 자원 수정
   ↓
lock 해제
```

특징:

- 소유권이 있음
- 잠금을 획득한 스레드가 해제하는 것이 원칙
- 상호 배제를 목적으로 사용

```python
with lock:
    count += 1
```

### 6. 세마포어(Semaphore)

정수 카운터를 이용해 동시에 접근 가능한 실행 흐름 수를 제한한다.

- 이진 세마포어: 값이 0 또는 1
- 카운팅 세마포어: 여러 개의 동일 자원 관리

예: DB 연결이 최대 5개라면 세마포어 초기값을 5로 설정한다.

```text
wait(P): 카운터 감소, 자원이 없으면 대기
signal(V): 카운터 증가, 대기 중인 작업 깨움
```

### 7. 뮤텍스와 세마포어 비교

| 구분 | 뮤텍스 | 세마포어 |
|---|---|---|
| 목적 | 상호 배제 | 자원 개수 제어, 실행 순서 제어 |
| 값 | 잠김/해제 | 0 이상의 정수 |
| 소유권 | 있음 | 일반적으로 없음 |
| 해제 주체 | 잠금을 획득한 실행 흐름 | 다른 실행 흐름도 가능 |
| 예시 | 공유 변수 보호 | 연결 풀, 작업 슬롯 제한 |

### 8. 모니터(Monitor)

공유 자원과 해당 자원에 접근하는 연산을 하나로 묶고, 내부적으로 상호 배제를 보장하는 고수준 동기화 구조다.

조건 변수를 사용해 특정 조건이 만족될 때까지 기다릴 수 있다.

- `wait()`
- `signal()` 또는 `notify()`

### 9. 스핀락(Spinlock)

락을 얻을 때까지 반복 확인하는 방식이다.

```text
while lock이 잠겨 있음:
    계속 확인
```

장점:

- 대기 시간이 매우 짧다면 문맥 교환을 피할 수 있음

단점:

- 기다리는 동안 CPU를 계속 소비
- 긴 대기에는 부적합

### 10. 원자적 연산(Atomic Operation)

중간에 끊기지 않고 하나의 단위로 실행되는 연산이다.

예:

- Compare-And-Swap
- Test-And-Set
- Atomic increment

원자적 연산을 활용하면 단순 카운터나 락 구현에서 경쟁 상태를 줄일 수 있다.

### 11. 동기화가 일으키는 문제

#### 기아 상태(Starvation)

특정 실행 흐름이 자원을 계속 얻지 못하고 무한히 기다리는 상태다.

예: 우선순위가 높은 스레드가 계속 실행되어 낮은 우선순위 스레드가 CPU를 얻지 못함.

#### 우선순위 역전(Priority Inversion)

낮은 우선순위 스레드가 높은 우선순위 스레드에 필요한 락을 보유하여, 높은 우선순위 스레드가 대기하는 현상이다.

해결 방법:

- 우선순위 상속
- 우선순위 상한 프로토콜

#### 라이브락(Livelock)

실행 흐름들이 멈추지는 않지만 서로 양보만 반복하여 실제 작업이 진행되지 않는 상태다.

```text
A: B에게 양보
B: A에게 양보
A: 다시 B에게 양보
...
```

## 3.3.8 교착 상태

### 1. 교착 상태란?

둘 이상의 프로세스 또는 스레드가 서로가 보유한 자원을 기다리며 무한히 대기하는 상태다.

```text
스레드 A: 자원 1 보유 → 자원 2 기다림
스레드 B: 자원 2 보유 → 자원 1 기다림
```

둘 다 필요한 자원을 얻지 못하므로 실행이 진행되지 않는다.

### 2. 교착 상태 발생 예시

```text
스레드 A
1. Lock A 획득
2. Lock B 획득 시도

스레드 B
1. Lock B 획득
2. Lock A 획득 시도
```

실행 순서가 다음과 같다면:

```text
A가 Lock A 획득
B가 Lock B 획득
A는 Lock B 대기
B는 Lock A 대기
→ 교착 상태
```

### 3. 교착 상태 발생 조건

교착 상태는 다음 네 조건이 모두 만족될 때 발생할 수 있다.

#### ① 상호 배제(Mutual Exclusion)

자원을 한 번에 하나의 실행 흐름만 사용할 수 있다.

#### ② 점유 대기(Hold and Wait)

하나 이상의 자원을 보유한 채 다른 자원을 기다린다.

#### ③ 비선점(No Preemption)

다른 실행 흐름이 보유한 자원을 강제로 빼앗을 수 없다.

#### ④ 순환 대기(Circular Wait)

실행 흐름들이 원형으로 서로의 자원을 기다린다.

```text
P1 → P2의 자원 대기
P2 → P3의 자원 대기
P3 → P1의 자원 대기
```

> 네 조건 중 하나라도 제거하면 교착 상태를 예방할 수 있다.

### 4. 교착 상태 처리 방법

#### 예방(Prevention)

교착 상태의 네 조건 중 하나가 성립하지 않도록 설계한다.

예:

- 모든 자원을 한 번에 요청하여 점유 대기 제거
- 자원 획득 순서를 고정하여 순환 대기 제거
- 일부 자원에 선점 허용

장점:

- 교착 상태가 원천적으로 발생하지 않음

단점:

- 자원 활용률이 낮아질 수 있음
- 동시성이 감소할 수 있음

#### 회피(Avoidance)

자원 할당 전에 시스템이 안전 상태를 유지하는지 검사한다.

대표 알고리즘:

- 은행원 알고리즘(Banker's Algorithm)

##### 안전 상태

모든 프로세스가 특정 순서로 필요한 자원을 얻어 정상 종료할 수 있는 상태다.

##### 불안전 상태

현재 교착 상태는 아니지만 이후 교착 상태가 발생할 가능성이 있는 상태다.

```text
안전 상태 ⊂ 교착 상태가 아닌 상태
불안전 상태 ≠ 즉시 교착 상태
```

회피 방식은 각 프로세스의 최대 자원 요구량을 미리 알아야 한다는 한계가 있다.

#### 탐지와 회복(Detection and Recovery)

교착 상태 발생을 허용한 뒤 주기적으로 탐지하고 해결한다.

탐지:

- 자원 할당 그래프
- 대기 그래프
- 탐지 알고리즘

회복:

- 교착 상태 프로세스 강제 종료
- 일부 프로세스를 이전 상태로 롤백
- 자원 선점
- 우선순위나 비용을 고려해 희생 프로세스 선택

#### 무시(Ostrich Algorithm)

교착 상태 발생 가능성이 낮고 예방 비용이 더 크다고 판단되면 특별히 처리하지 않는 방식이다.

일반적인 범용 운영체제는 일부 자원에 대해 이 접근을 사용하기도 한다.

### 5. 자원 할당 그래프

프로세스와 자원의 관계를 그래프로 표현한다.

```text
프로세스 → 자원 : 해당 자원을 요청
자원 → 프로세스 : 해당 자원이 프로세스에 할당
```

자원마다 인스턴스가 하나뿐인 경우 그래프에 사이클이 있으면 교착 상태다.

자원 인스턴스가 여러 개라면 사이클이 존재해도 반드시 교착 상태인 것은 아니다.

### 6. 실무에서의 교착 상태 예방

#### 락 획득 순서를 통일

```text
모든 스레드는 항상 Lock A → Lock B 순서로 획득
```

반대 순서로 획득하지 않으면 순환 대기를 막을 수 있다.

#### 중첩 락 최소화

가능한 한 하나의 락을 보유한 상태에서 다른 락을 요청하지 않는다.

#### 타임아웃 사용

락을 일정 시간 안에 얻지 못하면 보유한 락을 해제하고 다시 시도한다.

#### 임계 영역 최소화

락을 잡은 상태에서는 필요한 작업만 빠르게 수행한다.

특히 다음 작업을 임계 영역 안에서 오래 수행하지 않는 것이 좋다.

- 네트워크 요청
- 디스크 입출력
- 사용자 입력 대기
- 긴 계산
- 다른 스레드 종료 대기

#### 고수준 동시성 도구 사용

직접 여러 락을 관리하기보다 검증된 도구를 사용한다.

- Thread-safe Queue
- Concurrent Map
- Actor Model
- 작업 큐
- 트랜잭션
- 비동기 메시지 전달

### 7. 교착 상태, 기아 상태, 라이브락 비교

| 구분 | 상태 |
|---|---|
| 교착 상태 | 서로 자원을 기다리며 모두 멈춤 |
| 기아 상태 | 특정 실행 흐름만 계속 자원을 얻지 못함 |
| 라이브락 | 실행은 계속되지만 실질적인 진전이 없음 |

# 전체 구조 한눈에 보기

```text
프로그램
  │
  │ 컴파일, 링크
  ▼
실행 파일
  │
  │ 로더가 메모리에 적재
  ▼
프로세스
  ├─ 독립적인 가상 주소 공간
  ├─ PCB
  ├─ 코드 / 데이터 / BSS / 힙
  └─ 하나 이상의 스레드
       ├─ 프로그램 카운터
       ├─ 레지스터
       └─ 스택

여러 프로세스 → IPC로 통신
여러 스레드   → 메모리 공유

메모리 공유
  ↓
경쟁 상태 가능
  ↓
임계 영역 보호 필요
  ↓
뮤텍스, 세마포어, 모니터 등 사용
  ↓
락을 잘못 사용하면 교착 상태 가능
```

# 자주 헷갈리는 내용

### 1. 프로세스는 프로그램과 같은가?

아니다.

- 프로그램: 저장 장치의 정적 파일
- 프로세스: 실행을 위해 메모리와 운영체제 자원이 할당된 동적 상태

### 2. 스레드는 힙을 각각 가지는가?

아니다. 같은 프로세스의 스레드는 힙을 공유한다.

각 스레드가 따로 가지는 대표적인 자원은 스택, 레지스터, 프로그램 카운터다.

### 3. 멀티스레딩이면 무조건 빠른가?

아니다.

다음 요소에 따라 오히려 느려질 수 있다.

- 락 경쟁
- 문맥 교환
- 캐시 미스
- 순차 실행 구간
- 스레드 생성 비용
- CPU 코어 수
- GIL과 같은 런타임 제약

### 4. 락을 쓰면 경쟁 상태가 모두 해결되는가?

올바른 범위에 동일한 락을 사용해야 한다.

공유 자원에 접근하는 일부 코드만 락을 사용하거나 서로 다른 락을 사용하면 경쟁 상태가 계속 발생할 수 있다.

### 5. 사이클이 있으면 항상 교착 상태인가?

자원 인스턴스가 하나씩이라면 사이클은 교착 상태를 의미한다.

자원 인스턴스가 여러 개라면 사이클은 교착 상태의 가능성을 나타내지만 반드시 교착 상태라고 단정할 수 없다.

### 6. 비동기 처리와 멀티스레딩은 같은가?

아니다.

- 비동기: 작업 완료를 기다리는 동안 실행 흐름을 막지 않는 프로그래밍 구조
- 멀티스레딩: 여러 스레드를 사용해 작업을 실행하는 구조

비동기 처리는 단일 스레드 이벤트 루프로 구현할 수도 있다.

# 예상 면접 질문

### Q1. 프로세스와 스레드의 차이를 설명해 주세요.

프로세스는 운영체제로부터 독립적인 주소 공간과 자원을 할당받는 실행 단위이고, 스레드는 프로세스 내부에서 실제 명령어를 실행하는 단위다. 같은 프로세스의 스레드는 코드, 데이터, 힙, 열린 파일을 공유하지만 프로그램 카운터, 레지스터, 스택은 각각 가진다. 스레드는 생성과 문맥 교환 비용이 작지만 공유 자원 동기화가 필요하고, 하나의 스레드 오류가 전체 프로세스에 영향을 줄 수 있다.

### Q2. 문맥 교환이란 무엇인가요?

CPU가 실행할 프로세스나 스레드를 변경할 때 현재 작업의 프로그램 카운터와 레지스터 등의 실행 상태를 PCB 또는 TCB에 저장하고, 다음 작업의 상태를 복원하는 과정이다. 문맥 교환 중에는 사용자 작업이 진행되지 않으므로 빈번하게 발생하면 성능 저하를 일으킨다.

### Q3. 스레드마다 스택이 필요한 이유는 무엇인가요?

각 스레드는 독립적으로 함수를 호출하고 실행한다. 함수 매개변수, 지역 변수, 반환 주소와 같은 호출 정보를 분리해서 관리해야 하므로 스레드마다 별도의 스택이 필요하다.

### Q4. 경쟁 상태와 교착 상태의 차이는 무엇인가요?

경쟁 상태는 여러 실행 흐름의 접근 순서에 따라 공유 자원의 결과가 달라지는 문제다. 교착 상태는 여러 실행 흐름이 서로가 보유한 자원을 기다리며 영원히 진행하지 못하는 상태다.

### Q5. 뮤텍스와 세마포어의 차이는 무엇인가요?

뮤텍스는 일반적으로 하나의 임계 영역에 한 실행 흐름만 진입하도록 하는 소유권 기반 잠금이다. 세마포어는 정수 카운터를 이용해 동시에 사용할 수 있는 자원의 개수를 제어하며, 반드시 획득한 실행 흐름이 해제해야 하는 것은 아니다.

### Q6. 교착 상태의 네 가지 조건은 무엇인가요?

상호 배제, 점유 대기, 비선점, 순환 대기다. 네 조건이 모두 성립해야 교착 상태가 발생할 수 있으며, 하나라도 제거하면 교착 상태를 예방할 수 있다.

### Q7. CPU 집약적 작업과 I/O 집약적 작업에는 어떤 방식을 사용해야 하나요?

일반적으로 CPU 집약적 작업은 여러 코어를 활용할 수 있는 멀티프로세싱이 적합하고, I/O 집약적 작업은 대기 시간 동안 다른 작업을 수행할 수 있는 멀티스레딩이나 비동기 처리가 적합하다. 다만 실제 선택은 언어 런타임, 작업 크기, 데이터 전달 비용, 라이브러리의 병렬 처리 지원을 함께 고려해야 한다.
