# 2.5 HTTP

## 학습 목표

이 단원에서는 웹 통신의 핵심 프로토콜인 **HTTP**를 학습한다.

HTTP는 웹 브라우저와 웹 서버가 데이터를 주고받기 위한 애플리케이션 계층 프로토콜이다.
HTTP는 처음에는 단순한 문서 전송 프로토콜이었지만, 웹 서비스가 복잡해지면서 성능, 보안, 효율성을 개선하는 방향으로 발전해왔다.

학습 후 다음 내용을 설명할 수 있어야 한다.

* HTTP의 기본 개념
* HTTP/1.0의 특징과 한계
* HTTP/1.1의 Keep-Alive와 파이프라이닝
* HTTP/2의 멀티플렉싱과 헤더 압축
* HTTPS의 필요성과 TLS
* HTTP/3가 UDP 기반 QUIC을 사용하는 이유
* HTTP 버전별 차이

---

# HTTP 기본 개념

## 1. HTTP란?

**HTTP**는 HyperText Transfer Protocol의 약자이다.
클라이언트와 서버가 웹에서 데이터를 주고받기 위한 프로토콜이다.

일반적으로 클라이언트는 웹 브라우저이고, 서버는 웹 서버이다.

```text id="vzpal0"
Client ── HTTP Request ──> Server
Client <── HTTP Response ── Server
```

예를 들어 사용자가 브라우저에서 웹사이트에 접속하면, 브라우저는 서버에게 HTTP 요청을 보내고 서버는 HTTP 응답을 반환한다.

---

## 2. HTTP 요청과 응답

## HTTP Request

클라이언트가 서버에게 보내는 요청이다.

예시:

```http id="pyajvd"
GET /index.html HTTP/1.1
Host: example.com
User-Agent: Mozilla/5.0
```

요청은 보통 다음 요소로 구성된다.

| 구성 요소   | 설명                             |
| ------- | ------------------------------ |
| Method  | GET, POST, PUT, DELETE 등 요청 방식 |
| Path    | 요청 대상 경로                       |
| Version | HTTP 버전                        |
| Header  | 요청에 대한 부가 정보                   |
| Body    | 서버로 전달할 실제 데이터                 |

---

## HTTP Response

서버가 클라이언트에게 보내는 응답이다.

예시:

```http id="eaoqaq"
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 1256

<html>
  ...
</html>
```

응답은 보통 다음 요소로 구성된다.

| 구성 요소          | 설명                 |
| -------------- | ------------------ |
| Version        | HTTP 버전            |
| Status Code    | 요청 처리 결과           |
| Status Message | 상태 코드 설명           |
| Header         | 응답에 대한 부가 정보       |
| Body           | 클라이언트에게 전달할 실제 데이터 |

---

## 3. HTTP의 특징

HTTP의 대표적인 특징은 다음과 같다.

| 특징          | 설명                            |
| ----------- | ----------------------------- |
| 클라이언트-서버 구조 | 클라이언트가 요청하고 서버가 응답한다.         |
| 무상태성        | 서버가 이전 요청 상태를 기본적으로 기억하지 않는다. |
| 비연결성        | 요청과 응답 후 연결을 종료하는 방식에서 출발했다.  |
| 확장성         | 헤더를 통해 기능을 쉽게 확장할 수 있다.       |

---

## 4. HTTP의 무상태성

HTTP는 기본적으로 **무상태 프로토콜**이다.

무상태성이란 서버가 이전 요청 정보를 기본적으로 기억하지 않는다는 뜻이다.

예를 들어 클라이언트가 다음과 같이 요청한다고 하자.

```text id="k0qt1j"
1. 로그인 요청
2. 장바구니 조회 요청
3. 결제 요청
```

HTTP 자체만 보면 각각의 요청은 독립적이다.
서버는 두 번째 요청이 첫 번째 로그인 요청과 관련된 요청인지 자동으로 알 수 없다.

그래서 실제 웹 서비스에서는 상태 유지를 위해 다음 기술을 사용한다.

* 쿠키
* 세션
* 토큰
* JWT
* Authorization 헤더

---

## 5. HTTP 메서드

HTTP 메서드는 클라이언트가 서버에게 원하는 작업을 표현한다.

| 메서드     | 의미              | 예시          |
| ------- | --------------- | ----------- |
| GET     | 데이터 조회          | 게시글 목록 조회   |
| POST    | 데이터 생성 또는 처리 요청 | 회원가입, 로그인   |
| PUT     | 리소스 전체 수정       | 회원 정보 전체 수정 |
| PATCH   | 리소스 일부 수정       | 닉네임만 수정     |
| DELETE  | 리소스 삭제          | 게시글 삭제      |
| HEAD    | 응답 본문 없이 헤더만 조회 | 파일 존재 여부 확인 |
| OPTIONS | 서버가 지원하는 메서드 확인 | CORS 사전 요청  |

---

## 6. HTTP 상태 코드

HTTP 상태 코드는 서버가 요청을 어떻게 처리했는지 나타낸다.

| 범위  | 의미       | 예시                                               |
| --- | -------- | ------------------------------------------------ |
| 1xx | 정보성 응답   | 100 Continue                                     |
| 2xx | 성공       | 200 OK, 201 Created                              |
| 3xx | 리다이렉션    | 301 Moved Permanently, 302 Found                 |
| 4xx | 클라이언트 오류 | 400 Bad Request, 401 Unauthorized, 404 Not Found |
| 5xx | 서버 오류    | 500 Internal Server Error, 502 Bad Gateway       |

자주 쓰이는 상태 코드는 다음과 같다.

| 상태 코드                     | 의미             |
| ------------------------- | -------------- |
| 200 OK                    | 요청 성공          |
| 201 Created               | 리소스 생성 성공      |
| 204 No Content            | 성공했지만 응답 본문 없음 |
| 301 Moved Permanently     | 영구 이동          |
| 302 Found                 | 임시 이동          |
| 400 Bad Request           | 잘못된 요청         |
| 401 Unauthorized          | 인증 필요          |
| 403 Forbidden             | 권한 없음          |
| 404 Not Found             | 리소스 없음         |
| 500 Internal Server Error | 서버 내부 오류       |
| 502 Bad Gateway           | 게이트웨이 오류       |
| 503 Service Unavailable   | 서비스 사용 불가      |

---

# 2.5.1 HTTP/1.0

## 1. HTTP/1.0이란?

**HTTP/1.0**은 초기 웹 환경에서 사용된 HTTP 버전이다.
하나의 요청에 대해 하나의 TCP 연결을 사용하는 방식이 기본이었다.

즉, 클라이언트가 서버에서 HTML, CSS, 이미지 파일을 각각 받아야 한다면 매번 TCP 연결을 새로 생성해야 했다.

```text id="h8c4cm"
HTML 요청 → TCP 연결 생성 → 응답 → 연결 종료
CSS 요청  → TCP 연결 생성 → 응답 → 연결 종료
이미지 요청 → TCP 연결 생성 → 응답 → 연결 종료
```

---

## 2. HTTP/1.0의 동작 방식

HTTP/1.0에서는 기본적으로 요청 하나마다 TCP 연결을 새로 만든다.

```text id="hm0kao"
Client ── TCP 연결 ── Server
Client ── HTTP 요청 ──> Server
Client <── HTTP 응답 ── Server
TCP 연결 종료
```

웹 페이지 하나를 로딩하는 데 여러 리소스가 필요하다면 그만큼 연결 생성과 종료가 반복된다.

---

## 3. HTTP/1.0의 문제점

## TCP 연결 비용 증가

TCP는 연결을 만들 때 **3-way handshake**를 수행한다.

```text id="bppkas"
SYN → SYN/ACK → ACK
```

요청마다 이 과정을 반복하면 지연 시간이 증가한다.

---

## 많은 리소스를 불러오기 비효율적

현대 웹 페이지는 보통 여러 파일로 구성된다.

* HTML
* CSS
* JavaScript
* 이미지
* 폰트
* API 응답

HTTP/1.0 방식에서는 각 리소스마다 연결을 만들고 끊어야 하므로 비효율적이다.

---

## 서버 부하 증가

연결 생성과 종료가 자주 발생하면 서버도 더 많은 비용을 부담한다.

서버 입장에서는 다음 작업이 반복된다.

* TCP 연결 생성
* 소켓 관리
* 요청 처리
* 응답 전송
* TCP 연결 종료

---

## 4. HTTP/1.0의 한계 정리

| 한계              | 설명                    |
| --------------- | --------------------- |
| 연결 재사용 어려움      | 요청마다 TCP 연결 생성        |
| 지연 시간 증가        | 매번 3-way handshake 발생 |
| 서버 부하 증가        | 연결 생성/종료 반복           |
| 리소스 많은 페이지에 비효율 | 이미지, CSS, JS마다 연결 필요  |

---

## 5. 면접 포인트

HTTP/1.0은 요청마다 TCP 연결을 생성하고 응답 후 연결을 종료하는 방식이 기본이다.
웹 페이지에 여러 리소스가 포함되면 연결 생성 비용이 반복되어 지연 시간과 서버 부하가 증가한다.

---

# 2.5.2 HTTP/1.1

## 1. HTTP/1.1이란?

**HTTP/1.1**은 HTTP/1.0의 비효율을 개선한 버전이다.

가장 큰 특징은 다음과 같다.

* 지속 연결
* Keep-Alive
* 파이프라이닝
* Host 헤더
* 청크 전송
* 캐시 제어 개선

---

## 2. 지속 연결

HTTP/1.1에서는 기본적으로 TCP 연결을 재사용한다.
이를 **Persistent Connection**, 즉 지속 연결이라고 한다.

```text id="qa5awq"
TCP 연결 생성
↓
HTML 요청 / 응답
↓
CSS 요청 / 응답
↓
JS 요청 / 응답
↓
이미지 요청 / 응답
↓
TCP 연결 종료
```

HTTP/1.0처럼 요청마다 연결을 만들지 않아도 되므로 성능이 개선된다.

---

## 3. Keep-Alive

**Keep-Alive**는 TCP 연결을 일정 시간 동안 유지하여 여러 HTTP 요청과 응답에 재사용하는 방식이다.

HTTP/1.0에서는 Keep-Alive를 명시적으로 사용해야 했지만, HTTP/1.1에서는 지속 연결이 기본 동작이다.

HTTP/1.1에서 연결을 닫고 싶다면 다음 헤더를 사용할 수 있다.

```http id="dsaas3"
Connection: close
```

---

## 4. HTTP/1.1의 장점

| 장점          | 설명                    |
| ----------- | --------------------- |
| 연결 재사용      | TCP 연결 생성 비용 감소       |
| 지연 시간 감소    | 3-way handshake 반복 감소 |
| 서버 부하 감소    | 연결 생성/종료 횟수 감소        |
| 웹 페이지 로딩 개선 | 여러 리소스를 같은 연결에서 처리 가능 |

---

## 5. 파이프라이닝

HTTP/1.1에서는 **파이프라이닝**을 통해 응답을 기다리지 않고 여러 요청을 연속해서 보낼 수 있다.

```text id="ll9dkd"
요청1 → 요청2 → 요청3
응답1 ← 응답2 ← 응답3
```

하지만 응답은 요청 순서대로 와야 한다.

예를 들어 요청1의 응답이 늦어지면 요청2, 요청3의 응답도 뒤에서 기다려야 한다.

이를 **Head-of-Line Blocking**, 줄여서 HOL Blocking이라고 한다.

---

## 6. HTTP/1.1의 HOL Blocking

HTTP/1.1 파이프라이닝에서는 앞 요청의 응답이 지연되면 뒤 요청의 응답도 지연된다.

```text id="ec7gbv"
요청1: 느린 응답
요청2: 빠른 응답
요청3: 빠른 응답

하지만 응답 순서:
응답1 → 응답2 → 응답3
```

요청2와 요청3은 실제로 빨리 처리될 수 있어도, 응답1이 끝나기 전까지 클라이언트에게 먼저 전달되기 어렵다.

이 문제 때문에 HTTP/1.1 파이프라이닝은 실제 브라우저 환경에서 널리 활용되지 못했다.

---

## 7. Host 헤더

HTTP/1.1에서는 `Host` 헤더가 필수이다.

```http id="j4089l"
GET / HTTP/1.1
Host: example.com
```

Host 헤더가 필요한 이유는 하나의 IP 주소에서 여러 도메인을 운영할 수 있기 때문이다.

예를 들어 하나의 서버 IP에서 다음 사이트들을 함께 운영할 수 있다.

```text id="gx8rmi"
example.com
api.example.com
admin.example.com
```

서버는 Host 헤더를 보고 어떤 도메인으로 들어온 요청인지 구분한다.

---

## 8. 청크 전송

HTTP/1.1에서는 **Chunked Transfer Encoding**을 지원한다.

서버가 응답 전체 크기를 미리 알지 못해도 데이터를 조각 단위로 나누어 보낼 수 있다.

```http id="bl51j4"
Transfer-Encoding: chunked
```

예를 들어 큰 파일이나 스트리밍 응답을 보낼 때 유용하다.

---

## 9. HTTP/1.1의 한계

HTTP/1.1은 HTTP/1.0보다 개선되었지만 여전히 한계가 있다.

| 한계           | 설명                      |
| ------------ | ----------------------- |
| HOL Blocking | 앞 요청이 지연되면 뒤 요청도 지연     |
| 헤더 중복        | 매 요청마다 비슷한 헤더가 반복 전송    |
| 다중 요청 처리 비효율 | 한 연결에서 동시에 여러 응답 처리 어려움 |
| 많은 리소스 처리 한계 | 웹 페이지 리소스 증가에 비효율       |

---

## 10. 면접 포인트

HTTP/1.1은 지속 연결을 기본으로 사용하여 TCP 연결을 재사용한다.
이를 통해 HTTP/1.0의 연결 생성 비용을 줄였다.
하지만 요청과 응답 순서 문제로 HOL Blocking이 발생할 수 있고, 매 요청마다 중복 헤더가 전송되는 한계가 있다.

---

# 2.5.3 HTTP/2

## 1. HTTP/2란?

**HTTP/2**는 HTTP/1.1의 성능 문제를 개선하기 위해 등장한 버전이다.

HTTP/2의 핵심 특징은 다음과 같다.

* 바이너리 프레이밍
* 멀티플렉싱
* 스트림 기반 통신
* 헤더 압축
* 서버 푸시

---

## 2. 바이너리 프레이밍

HTTP/1.1은 사람이 읽기 쉬운 텍스트 기반 프로토콜이다.

예시:

```http id="do3px0"
GET /index.html HTTP/1.1
Host: example.com
```

반면 HTTP/2는 데이터를 바이너리 형식의 프레임으로 나누어 전송한다.

```text id="w8w9to"
HTTP 메시지
↓
Binary Frame
↓
전송
```

바이너리 형식을 사용하면 컴퓨터가 더 효율적으로 파싱하고 처리할 수 있다.

---

## 3. 스트림

HTTP/2에서는 하나의 TCP 연결 안에서 여러 개의 스트림을 사용할 수 있다.

**스트림**은 하나의 요청과 응답이 오가는 독립적인 흐름이다.

```text id="m3xx2i"
TCP Connection
 ├─ Stream 1: HTML 요청/응답
 ├─ Stream 3: CSS 요청/응답
 ├─ Stream 5: JS 요청/응답
 └─ Stream 7: 이미지 요청/응답
```

각 스트림은 독립적으로 처리될 수 있다.

---

## 4. 멀티플렉싱

**멀티플렉싱**은 하나의 TCP 연결에서 여러 요청과 응답을 동시에 주고받는 방식이다.

HTTP/1.1에서는 응답 순서 문제 때문에 앞 요청이 막히면 뒤 요청도 영향을 받았다.
HTTP/2는 여러 스트림을 섞어서 전송할 수 있기 때문에 HTTP/1.1의 HOL Blocking 문제를 크게 개선했다.

```text id="r77oa6"
HTTP/1.1:
요청1 → 응답1 → 요청2 → 응답2 → 요청3 → 응답3

HTTP/2:
요청1 ┐
요청2 ├─ 하나의 TCP 연결에서 동시 처리
요청3 ┘
응답2 ┐
응답1 ├─ 프레임 단위로 섞여서 전송 가능
응답3 ┘
```

---

## 5. HTTP/2의 HOL Blocking 한계

HTTP/2는 HTTP/1.1의 애플리케이션 계층 HOL Blocking을 해결했다.

하지만 HTTP/2는 여전히 TCP 위에서 동작한다.
따라서 TCP 계층에서 패킷 손실이 발생하면 같은 TCP 연결 안의 모든 스트림이 영향을 받을 수 있다.

즉, HTTP/2는 HTTP 레벨의 HOL Blocking은 개선했지만, TCP 레벨의 HOL Blocking 문제는 남아 있다.

이 한계를 해결하기 위해 HTTP/3가 등장했다.

---

## 6. 헤더 압축

HTTP 요청과 응답에는 많은 헤더가 포함된다.

예시:

```http id="x6su97"
User-Agent: Mozilla/5.0
Accept: text/html
Accept-Encoding: gzip, deflate, br
Cookie: session_id=abc123
```

문제는 여러 요청에서 비슷한 헤더가 반복된다는 점이다.

HTTP/2는 **HPACK**이라는 방식으로 헤더를 압축한다.

이를 통해 중복 헤더 전송을 줄이고 네트워크 사용량을 줄일 수 있다.

---

## 7. 서버 푸시

HTTP/2는 서버 푸시 기능을 제공한다.

서버 푸시는 클라이언트가 요청하지 않은 리소스도 서버가 미리 보내는 기능이다.

예를 들어 클라이언트가 HTML을 요청하면 서버는 CSS와 JS도 필요할 것이라고 판단해 함께 보낼 수 있다.

```text id="umhptm"
Client: HTML 주세요.
Server: HTML + CSS + JS를 함께 보냄.
```

다만 실제 웹 환경에서는 캐시 전략과 중복 전송 문제로 인해 서버 푸시는 기대만큼 널리 활용되지는 않았다.

---

## 8. HTTP/2의 장점

| 장점               | 설명                          |
| ---------------- | --------------------------- |
| 멀티플렉싱            | 하나의 TCP 연결에서 여러 요청/응답 동시 처리 |
| 헤더 압축            | 중복 헤더 전송량 감소                |
| 바이너리 프레이밍        | 효율적인 파싱과 전송                 |
| 연결 수 감소          | 여러 TCP 연결을 만들 필요 감소         |
| HTTP/1.1보다 빠른 성능 | 리소스 많은 웹 페이지에서 유리           |

---

## 9. HTTP/2의 한계

| 한계                  | 설명                |
| ------------------- | ----------------- |
| TCP 의존              | TCP 위에서 동작        |
| TCP 레벨 HOL Blocking | 패킷 손실 시 모든 스트림 영향 |
| 서버 푸시 활용 제한         | 캐시와 중복 전송 문제      |
| UDP 기반 최적화 불가       | TCP 연결 특성에 묶임     |

---

## 10. 면접 포인트

HTTP/2는 하나의 TCP 연결에서 여러 요청과 응답을 동시에 처리하는 멀티플렉싱을 제공한다.
또한 HPACK을 통한 헤더 압축으로 중복 헤더 전송을 줄인다.
하지만 TCP 기반이기 때문에 패킷 손실이 발생하면 모든 스트림이 영향을 받는 TCP 레벨 HOL Blocking 문제가 남아 있다.

---

# 2.5.4 HTTPS

## 1. HTTPS란?

**HTTPS**는 HyperText Transfer Protocol Secure의 약자이다.
HTTP에 보안 계층인 TLS를 적용한 프로토콜이다.

```text id="xww31j"
HTTP + TLS = HTTPS
```

HTTP는 데이터를 평문으로 전송한다.
따라서 중간에서 누군가 패킷을 가로채면 내용을 볼 수 있다.

HTTPS는 데이터를 암호화하여 전송하기 때문에 중간에서 가로채더라도 내용을 쉽게 알 수 없다.

---

## 2. HTTP의 보안 문제

HTTP는 다음과 같은 보안 문제가 있다.

## 도청

HTTP는 평문으로 데이터를 전송하기 때문에 중간자가 내용을 볼 수 있다.

```text id="lczejb"
아이디: taein
비밀번호: 1234
```

이런 정보가 암호화 없이 전송되면 매우 위험하다.

---

## 변조

중간자가 응답 내용을 바꿀 수 있다.

예를 들어 서버가 정상 HTML을 보냈는데, 중간자가 악성 스크립트를 삽입할 수 있다.

---

## 위장

클라이언트가 접속한 서버가 진짜 서버인지 확인하기 어렵다.

예를 들어 사용자가 은행 사이트에 접속했다고 생각했지만, 실제로는 공격자가 만든 가짜 사이트일 수 있다.

---

## 3. HTTPS가 제공하는 보안 요소

HTTPS는 TLS를 통해 다음을 제공한다.

| 보안 요소 | 설명                          |
| ----- | --------------------------- |
| 기밀성   | 데이터를 암호화해 중간자가 내용을 볼 수 없게 함 |
| 무결성   | 데이터가 전송 중 변조되지 않았는지 확인      |
| 인증    | 접속한 서버가 신뢰할 수 있는 서버인지 확인    |

---

## 4. TLS란?

**TLS**는 Transport Layer Security의 약자이다.
인터넷 통신에서 보안 채널을 만들기 위한 프로토콜이다.

과거에는 SSL이라는 용어를 많이 사용했지만, 현재는 TLS가 표준적으로 사용된다.

실무에서 “SSL 인증서”라고 부르는 것도 실제로는 TLS 인증서인 경우가 많다.

---

## 5. TLS 인증서

TLS 인증서는 서버의 신원을 증명하기 위한 전자 인증서이다.

인증서에는 보통 다음 정보가 포함된다.

* 도메인 이름
* 인증서 소유자 정보
* 공개키
* 인증서 발급 기관
* 유효 기간
* 전자 서명

브라우저는 인증서를 확인하여 현재 접속한 서버가 신뢰할 수 있는 서버인지 검증한다.

---

## 6. CA

**CA**는 Certificate Authority의 약자이다.
인증서를 발급하고 신뢰성을 보장하는 인증 기관이다.

브라우저와 운영체제는 신뢰할 수 있는 CA 목록을 가지고 있다.
서버가 제시한 인증서가 신뢰할 수 있는 CA에 의해 발급되었다면 브라우저는 해당 서버를 신뢰할 수 있다고 판단한다.

---

## 7. HTTPS 통신 과정

HTTPS 통신은 대략 다음 흐름으로 진행된다.

```text id="vkwox3"
1. 클라이언트가 서버에 HTTPS 접속 요청
2. 서버가 TLS 인증서 전달
3. 클라이언트가 인증서 검증
4. 클라이언트와 서버가 암호화 방식 협상
5. 세션 키 생성
6. 이후 데이터는 세션 키로 암호화하여 통신
```

---

## 8. 대칭키와 비대칭키

HTTPS에서는 대칭키 암호화와 비대칭키 암호화가 함께 사용된다.

## 비대칭키 암호화

공개키와 개인키를 사용하는 방식이다.

| 키   | 설명               |
| --- | ---------------- |
| 공개키 | 누구나 알 수 있는 키     |
| 개인키 | 서버만 가지고 있어야 하는 키 |

비대칭키 암호화는 인증과 키 교환 과정에서 사용된다.

---

## 대칭키 암호화

하나의 같은 키로 암호화와 복호화를 수행하는 방식이다.

HTTPS에서는 실제 데이터 전송에 대칭키가 사용된다.

그 이유는 대칭키 암호화가 비대칭키 암호화보다 빠르기 때문이다.

---

## 9. HTTPS의 장점

| 장점           | 설명                 |
| ------------ | ------------------ |
| 데이터 암호화      | 중간자가 내용을 볼 수 없음    |
| 데이터 무결성      | 전송 중 변조 여부 확인 가능   |
| 서버 인증        | 접속한 서버가 진짜인지 확인 가능 |
| SEO와 브라우저 신뢰 | 최신 웹 환경에서 기본 요구사항  |
| 로그인/결제 보호    | 민감 정보 전송에 필수       |

---

## 10. HTTPS의 한계

HTTPS를 사용한다고 해서 모든 보안 문제가 해결되는 것은 아니다.

HTTPS는 전송 구간을 보호할 뿐이다.

다음과 같은 문제는 별도로 대응해야 한다.

* 서버 자체가 해킹된 경우
* 클라이언트가 악성코드에 감염된 경우
* 피싱 사이트에 사용자가 직접 접속한 경우
* 애플리케이션 로직 취약점
* XSS, SQL Injection, CSRF 같은 웹 취약점

---

## 11. 면접 포인트

HTTPS는 HTTP에 TLS를 적용해 기밀성, 무결성, 인증을 제공하는 프로토콜이다.
HTTP는 평문으로 전송되기 때문에 도청과 변조 위험이 있지만, HTTPS는 데이터를 암호화하고 서버 인증서를 통해 접속한 서버의 신뢰성을 검증한다.

---

# 2.5.5 HTTP/3

## 1. HTTP/3란?

**HTTP/3**는 HTTP의 최신 주요 버전이다.
HTTP/2의 한계를 개선하기 위해 TCP 대신 **QUIC**을 사용한다.

```text id="iuh3c5"
HTTP/1.1: TCP 기반
HTTP/2: TCP 기반
HTTP/3: QUIC 기반
```

QUIC은 UDP 위에서 동작하는 전송 프로토콜이다.

```text id="c5fyyc"
HTTP/3
↓
QUIC
↓
UDP
↓
IP
```

---

## 2. HTTP/3가 등장한 이유

HTTP/2는 멀티플렉싱을 제공했지만 TCP 위에서 동작한다는 한계가 있었다.

TCP에서는 패킷 하나가 손실되면 그 뒤의 데이터 처리가 지연될 수 있다.
HTTP/2는 하나의 TCP 연결에서 여러 스트림을 처리하기 때문에, 패킷 손실이 발생하면 모든 스트림이 영향을 받을 수 있다.

이 문제를 줄이기 위해 HTTP/3는 TCP가 아니라 QUIC을 사용한다.

---

## 3. QUIC이란?

**QUIC**은 UDP 기반의 전송 프로토콜이다.
기존 TCP의 신뢰성 기능을 UDP 위에서 새롭게 구현한 방식으로 이해할 수 있다.

QUIC의 주요 특징은 다음과 같다.

* UDP 기반
* TLS 1.3 내장
* 빠른 연결 설정
* 스트림 단위 멀티플렉싱
* TCP 수준의 HOL Blocking 완화
* 연결 마이그레이션 지원

---

## 4. HTTP/3의 구조

HTTP/3는 TCP를 사용하지 않고 QUIC 위에서 동작한다.

```text id="cxfapj"
HTTP/2 구조:
HTTP/2
TLS
TCP
IP

HTTP/3 구조:
HTTP/3
QUIC + TLS 1.3
UDP
IP
```

HTTP/3에서는 TLS 1.3이 QUIC에 통합되어 있다.
따라서 보안 연결 설정이 더 효율적으로 이루어진다.

---

## 5. 빠른 연결 설정

HTTP/1.1이나 HTTP/2에서 HTTPS를 사용하면 TCP 연결과 TLS 연결 과정이 필요하다.

```text id="cofws6"
TCP handshake
↓
TLS handshake
↓
HTTP 요청
```

HTTP/3는 QUIC에서 연결 설정과 암호화 협상을 더 효율적으로 처리한다.

```text id="k8oq0e"
QUIC handshake
↓
HTTP 요청
```

이로 인해 연결 설정 지연 시간을 줄일 수 있다.

---

## 6. TCP 레벨 HOL Blocking 완화

HTTP/2는 하나의 TCP 연결 안에서 여러 스트림을 처리한다.

하지만 TCP는 바이트 스트림 기반이기 때문에 중간에 패킷이 손실되면 이후 데이터 처리가 막힐 수 있다.

```text id="moxdhd"
HTTP/2 over TCP:
패킷 손실 발생
↓
TCP 재전송 대기
↓
같은 연결의 여러 스트림이 영향받음
```

HTTP/3의 QUIC은 스트림을 독립적으로 처리한다.
한 스트림에서 패킷 손실이 발생해도 다른 스트림은 계속 처리될 수 있다.

```text id="g7chmq"
HTTP/3 over QUIC:
Stream 1 패킷 손실
↓
Stream 1만 영향
Stream 2, Stream 3은 계속 처리 가능
```

---

## 7. 연결 마이그레이션

HTTP/3는 연결 마이그레이션을 지원한다.

예를 들어 사용자가 스마트폰으로 웹 서비스를 이용하다가 네트워크가 바뀌는 상황을 생각해보자.

```text id="w71ojf"
Wi-Fi 사용 중
↓
LTE/5G로 전환
```

TCP 연결은 보통 IP 주소와 포트 정보에 강하게 묶여 있다.
네트워크가 바뀌어 IP가 달라지면 연결이 끊어질 수 있다.

반면 QUIC은 연결 ID를 사용하여 네트워크가 바뀌어도 기존 연결을 유지할 수 있다.

이 기능은 모바일 환경에서 특히 유리하다.

---

## 8. HTTP/3의 장점

| 장점              | 설명                     |
| --------------- | ---------------------- |
| 빠른 연결 설정        | QUIC을 통해 연결 지연 감소      |
| HOL Blocking 완화 | 스트림 단위 처리로 패킷 손실 영향 감소 |
| TLS 1.3 내장      | 보안 연결 기본 제공            |
| 연결 마이그레이션       | 네트워크 변경 시 연결 유지 가능     |
| 모바일 환경에 유리      | Wi-Fi와 LTE/5G 전환에 강함   |

---

## 9. HTTP/3의 한계

| 한계         | 설명                        |
| ---------- | ------------------------- |
| UDP 차단 가능성 | 일부 네트워크나 방화벽에서 UDP 트래픽 제한 |
| 운영 복잡도     | 서버, 로드밸런서, 방화벽 설정 필요      |
| 디버깅 난이도    | 암호화와 QUIC 구조로 패킷 분석이 어려움  |
| 인프라 지원 필요  | 서버와 클라이언트 모두 HTTP/3 지원 필요 |

---

## 10. 면접 포인트

HTTP/3는 HTTP/2의 TCP 기반 한계를 개선하기 위해 QUIC을 사용하는 HTTP 버전이다.
QUIC은 UDP 기반이며 TLS 1.3을 내장하고, 스트림 단위 멀티플렉싱을 제공해 TCP 레벨의 HOL Blocking 문제를 완화한다.
또한 연결 마이그레이션을 지원해 모바일 환경에서 네트워크가 바뀌어도 연결 유지에 유리하다.

---

# HTTP 버전별 발전 흐름

HTTP는 다음과 같은 문제를 해결하는 방향으로 발전했다.

```text id="eyp9fc"
HTTP/1.0
요청마다 TCP 연결 생성
↓
HTTP/1.1
지속 연결로 TCP 연결 재사용
↓
HTTP/2
멀티플렉싱과 헤더 압축
↓
HTTPS
TLS를 통한 보안 강화
↓
HTTP/3
QUIC 기반으로 TCP 한계 개선
```

---

# HTTP 버전별 비교

| 구분           | HTTP/1.0   | HTTP/1.1    | HTTP/2             | HTTP/3             |
| ------------ | ---------- | ----------- | ------------------ | ------------------ |
| 기반 전송        | TCP        | TCP         | TCP                | QUIC over UDP      |
| 연결 방식        | 요청마다 연결 생성 | 지속 연결 기본    | 하나의 TCP 연결에서 멀티플렉싱 | QUIC 연결에서 멀티플렉싱    |

# 핵심 요약

## HTTP

* HTTP는 웹에서 클라이언트와 서버가 데이터를 주고받기 위한 애플리케이션 계층 프로토콜이다.
* HTTP는 요청과 응답 구조를 가진다.
* HTTP는 기본적으로 무상태성을 가진다.
* 상태 유지를 위해 쿠키, 세션, 토큰 등을 사용한다.

## HTTP/1.0

* 요청마다 TCP 연결을 새로 생성하는 방식이 기본이다.
* 리소스가 많을수록 연결 생성 비용이 커진다.
* 3-way handshake가 반복되어 지연 시간이 증가한다.

## HTTP/1.1

* 지속 연결을 기본으로 사용한다.
* Keep-Alive를 통해 TCP 연결을 재사용한다.
* Host 헤더가 필수이다.
* 파이프라이닝을 지원하지만 HOL Blocking 문제가 있다.
* 청크 전송과 캐시 제어가 개선되었다.

## HTTP/2

* 바이너리 프레이밍을 사용한다.
* 하나의 TCP 연결에서 여러 스트림을 처리하는 멀티플렉싱을 지원한다.
* HPACK으로 헤더를 압축한다.
* HTTP/1.1의 HOL Blocking을 개선했지만 TCP 레벨의 HOL Blocking은 남아 있다.

## HTTPS

* HTTPS는 HTTP에 TLS를 적용한 보안 프로토콜이다.
* 기밀성, 무결성, 인증을 제공한다.
* TLS 인증서를 통해 서버의 신뢰성을 검증한다.
* 실제 데이터 전송에는 주로 대칭키 암호화가 사용된다.

## HTTP/3

* HTTP/3는 QUIC 기반으로 동작한다.
* QUIC은 UDP 위에서 동작한다.
* TLS 1.3이 내장되어 있다.
* 스트림 단위 멀티플렉싱으로 TCP 레벨 HOL Blocking을 완화한다.
* 연결 마이그레이션을 지원해 모바일 환경에 유리하다.

# 예상 질문

## Q1. HTTP란 무엇인가요?

HTTP는 웹에서 클라이언트와 서버가 데이터를 주고받기 위한 애플리케이션 계층 프로토콜입니다.
클라이언트가 요청을 보내면 서버가 응답을 반환하는 요청-응답 구조를 가집니다.

## Q2. HTTP의 무상태성이란 무엇인가요?

HTTP의 무상태성이란 서버가 이전 요청의 상태를 기본적으로 기억하지 않는다는 의미입니다.
각 요청은 독립적으로 처리되며, 상태 유지를 위해 쿠키, 세션, 토큰 등을 사용합니다.

## Q3. HTTP/1.0의 가장 큰 문제는 무엇인가요?

HTTP/1.0은 요청마다 TCP 연결을 새로 생성하고 응답 후 연결을 종료하는 방식이 기본입니다.
따라서 웹 페이지에 여러 리소스가 있으면 3-way handshake가 반복되어 지연 시간과 서버 부하가 증가합니다.

## Q4. HTTP/1.1은 HTTP/1.0의 문제를 어떻게 개선했나요?

HTTP/1.1은 지속 연결을 기본으로 사용하여 하나의 TCP 연결을 여러 요청과 응답에 재사용합니다.
이를 통해 TCP 연결 생성과 종료 비용을 줄였습니다.

## Q5. HTTP/1.1의 HOL Blocking이란 무엇인가요?

HTTP/1.1 파이프라이닝에서는 응답이 요청 순서대로 와야 합니다.
따라서 앞 요청의 응답이 지연되면 뒤 요청의 응답도 함께 지연되는 문제가 발생합니다.
이를 Head-of-Line Blocking이라고 합니다.

## Q6. HTTP/2의 핵심 특징은 무엇인가요?

HTTP/2의 핵심 특징은 바이너리 프레이밍, 멀티플렉싱, 스트림 기반 통신, 헤더 압축입니다.
하나의 TCP 연결에서 여러 요청과 응답을 동시에 처리할 수 있어 HTTP/1.1보다 효율적입니다.

## Q7. HTTP/2에서도 HOL Blocking 문제가 남아 있는 이유는 무엇인가요?

HTTP/2는 TCP 위에서 동작합니다.
TCP에서는 패킷 손실이 발생하면 손실된 패킷이 재전송될 때까지 이후 데이터 처리가 지연될 수 있습니다.
따라서 같은 TCP 연결 안의 여러 스트림이 영향을 받을 수 있습니다.

## Q8. HTTPS는 무엇인가요?

HTTPS는 HTTP에 TLS를 적용한 보안 프로토콜입니다.
데이터를 암호화하여 기밀성을 제공하고, 데이터 변조 여부를 확인하며, 인증서를 통해 서버의 신뢰성을 검증합니다.

## Q9. TLS 인증서는 왜 필요한가요?

TLS 인증서는 클라이언트가 접속한 서버가 실제 신뢰할 수 있는 서버인지 확인하기 위해 필요합니다.
브라우저는 인증서가 신뢰할 수 있는 CA에 의해 발급되었는지 검증합니다.

## Q10. HTTP/3는 왜 UDP를 사용하나요?

HTTP/3는 TCP의 한계를 개선하기 위해 UDP 기반의 QUIC을 사용합니다.
QUIC은 UDP 위에서 신뢰성, 암호화, 멀티플렉싱을 구현하고, 스트림 단위로 패킷 손실 영향을 줄여 TCP 레벨 HOL Blocking 문제를 완화합니다.

## Q11. HTTP/2와 HTTP/3의 가장 큰 차이는 무엇인가요?

HTTP/2는 TCP 기반이고, HTTP/3는 QUIC over UDP 기반입니다.
HTTP/3는 QUIC을 사용해 연결 설정을 빠르게 하고, 패킷 손실이 발생했을 때 다른 스트림에 미치는 영향을 줄입니다.
